Welcome to the ownership handbook for the Semantic Analysis and IR Generation phases of our Source-to-Source Compiler. Let's start with the fundamental theory behind these phases.

SEMANTIC ANALYSIS
-----------------

**What is Semantic Analysis in a Compiler?**
While the parser checks if a sentence is grammatically correct (syntax), the semantic analyzer checks if the sentence actually makes sense (meaning). For example, "Colorless green ideas sleep furiously" is grammatically valid, but semantically nonsensical. In programming, `int x = "hello";` is syntactically fine (Type ID = String), but semantically invalid because you cannot assign a string to an integer variable. Semantic analysis enforces the rules of the programming language.

**Difference between Parsing and Semantic Analysis:**
- **Parsing (Syntax):** Ensures code matches the language grammar (e.g., `a + b` is valid syntax). Produces an Abstract Syntax Tree (AST).
- **Semantic Analysis:** Walks the AST to ensure rules are followed: Are `a` and `b` declared? Are they numbers? Can they be added together?

**Role of Semantic Analyzer in this Project:**
Our transpiler converts code between Python, C, and C++. The semantic analyzer sits right after parsing. Its job is to guarantee that the AST is 100% valid before we try to generate target code. If semantic analysis passes, the code generation phase is guaranteed to succeed without crashing.

**Inputs and Outputs:**
- **Input:** An unverified Abstract Syntax Tree (AST) generated by the parser.
- **Output:** An annotated, verified AST (where types are inferred and checked), along with a Symbol Table (a dictionary of all variables, arrays, and functions for the UI).

**Symbol Tables:**
A symbol table is a data structure used by the compiler to keep track of semantics of variables. It stores the name of the variable, its type, scope, and where it was declared. In our project, it's implemented as a list of dictionaries (`self.scope_stack`), and a flattened dictionary (`self.symbol_table`) is generated for UI rendering.

**Scope Handling:**
Scope defines the visibility of variables. Variables declared inside a function shouldn't be accessible outside. 
We manage this using a `scope_stack`. 
- Global scope is `scope_stack[0]`.
- When entering a function, block, or loop, we push a new empty dictionary to the stack (`self._enter_scope()`).
- When looking up a variable (`self._lookup()`), we search from the top of the stack (innermost scope) down to the bottom (global scope).
- When exiting a block, we pop the top dictionary (`self._exit_scope()`), effectively destroying those local variables.

**Type Checking & Variable Validation:**
Every expression's type is evaluated recursively. If you try to do `x + y`, the analyzer looks up `x` and `y`, determines their types, and decides if they can be added. It also validates that variables are declared before they are used, which is critical since a typo like `countr = count + 1` must be caught here.

**Function Signature Checking:**
When a function is called, the analyzer checks if it exists, if the correct number of arguments are passed, and if the argument types match the expected parameter types.

**Two-Pass Semantic Analysis Logic:**
In C/C++, you must declare a function before you call it (single-pass analysis works fine). However, in Python, you can call a function that is defined later in the file, as long as it's defined before it's executed. 
To support this "forward calling" in Python, our analyzer uses a **Two-Pass approach**:
- **Pass 1:** Scans the whole program and registers all function signatures (names, parameters, return types) into the global scope. No bodies are analyzed yet.
- **Pass 2:** Analyzes the actual code. Since all functions were registered in Pass 1, a call to a function defined lower down will succeed because its signature is already known.

**Type Promotion Logic:**
When adding an `int` and a `float`, the result is a `float`. The analyzer uses a `_promote` algorithm to determine the resulting type of binary operations, mimicking standard language behaviors (INT+INT=INT, INT+FLOAT=FLOAT).

**Error Collection Strategy:**
Instead of crashing on the first error, the analyzer collects *all* errors into an `errors` list and raises a `CompilerErrorList` at the very end. This is a much better user experience, showing the user all their mistakes at once rather than forcing them to recompile iteratively for every single bug.

**Supported vs Rejected Semantic Constructs:**
- Supported: Type promotion, scoping, forward calls in Python, basic types (int, float, bool, limited str).
- Rejected: String concatenation (strings are only for `print`), redefining variables in the same scope, unsupported type assignments (assigning float to int without explicit cast logic in some cases).

**Why this architecture?**
It's designed to be simple yet robust. The visitor pattern (using `isinstance` checks) over the dataclass AST provides a clear, highly readable structure. It avoids complex visitor classes in favor of straightforward recursive methods.

IR GENERATION
-------------

**What is Intermediate Representation (IR)?**
IR is the data structure or code used internally by a compiler to represent source code. It sits between the frontend (parser/semantic) and the backend (code generator). 

**Why IR is needed:**
IR decouples the source language from the target language. Instead of writing N*M translators (e.g., Python to C, Python to C++, C to Python...), you translate Source -> IR, and then IR -> Target. 

**Why a language-neutral AST-based IR was chosen:**
Our project uses the **Abstract Syntax Tree itself as the IR**. 
- Why not TAC (Three-Address Code)? TAC breaks complex expressions into simple instructions (`t1 = x + y`). This destroys the program's structure. Since we are doing source-to-source translation (e.g., C to Python), we *want* to preserve the high-level `x + y` structure so the generated Python code is readable.
- Why not LLVM IR? LLVM is too low-level, focused on assembly generation, and requires the massive LLVM toolchain.

**Structure of this project's IR:**
The IR phase in our project (`ir_generator.py`) acts as a structural integrity checkpoint and a JSON serializer. It verifies that the AST generated and typed by the semantic analyzer is perfectly formed according to our Dataclass definitions. 

**Role of IR before code generation:**
It acts as an absolute firewall. If the AST passes IR validation, the Code Generators can assume the AST is structurally flawless, reducing the need for error checking in the generators. It also converts the AST to a dictionary format so the web UI can render it visually.

2. TOOLS, TECHNIQUES AND ALGORITHMS USED
==================================================

**Python Dataclasses:**
- **What it is:** The `@dataclass` decorator automatically generates boilerplate methods like `__init__`, `__repr__`, and `__eq__`.
- **Why used:** It makes defining AST nodes (`ast_nodes.py`) incredibly clean and self-documenting.
- **Where used:** The entire AST structure.
- **Why chosen:** Better than plain dictionaries (provides type hints, IDE autocomplete, prevents typos in keys) and better than standard classes (saves hundreds of lines of boilerplate).

**Symbol Table Design (Stack of Dicts):**
- **What it is:** `self.scope_stack = [{}]`. A list where each element is a dictionary representing a scope level.
- **Why used:** To implement variable shadowing and scoping rules natively. Pushing to the list enters a scope; popping exits it.
- **Where used:** `SemanticAnalyzer._enter_scope`, `_exit_scope`, `_declare`, `_lookup`.

**Recursive Traversal (Visitor Pattern alternative):**
- **What it is:** The `_analyze_stmt` and `_check_node` functions look at a node's type using `isinstance` and route it to the specific handler function (e.g., `_do_if`).
- **Why used:** To walk the tree.
- **Why chosen:** Standard Pythonic way to handle ASTs. It's simpler to understand for a viva defense than a complex dynamic dispatch class like Python's built-in `ast.NodeVisitor`.

**Two-Pass Analysis Algorithm:**
- **What it is:** Scanning the AST twice.
- **Why used:** To resolve the "Forward Declaration" problem in Python, allowing functions to call other functions defined later in the file.

**Type Inference / Promotion:**
- **What it is:** Deducing the type of an expression. If `node.data_type == DataType.UNKNOWN`, the analyzer figures it out by evaluating the right-hand side.
- **Why used:** Python variables don't have explicit types. The compiler *must* infer them to generate typed C/C++ code.

**Error Batching:**
- **What it is:** `self.errors.append(...)` instead of `raise`.
- **Why used:** Collects all semantic and structural errors in one pass to show the user a comprehensive list, significantly improving developer experience.

**Scope Helpers:**
```python
    def _enter_scope(self):
        self.scope_stack.append({})
```
- Pushes a new empty dictionary. Used when entering an `if`, `while`, `for`, or function body.

```python
    def _exit_scope(self):
        if len(self.scope_stack) > 1:
            self.scope_stack.pop()
```
- Destroys the current scope. Protects against popping the global scope (index 0).

```python
    def _declare(self, name, info, line):
```
- Registers a variable in the current scope.
- `scope = self.scope_stack[-1]` -> Gets innermost scope.
- `if name in scope:` -> Checks for redeclaration in the SAME scope. If it exists, append a `CompilerError`.
- `scope[name] = info` -> Adds the variable to the compiler's internal scope tracker.
- Next lines generate a key (`func.var` or `var`) and save it to the flat `self.symbol_table` for UI visualization.

```python
    def _lookup(self, name):
        for scope in reversed(self.scope_stack):
            if name in scope: return scope[name]
        return None
```
- Searches scopes from innermost (last in list) to global (first in list). Returns the variable info or `None` if undeclared.

**Passes Logic:**
```python
    def _pass1(self, program):
```
- **Python Pass 1:** Iterates `program.functions`. Checks for duplicate names. Registers the name, parameter types, and return type into `self.functions`, the global scope `self.scope_stack[0]`, and the UI `symbol_table`. Does NOT look at `func.body`.

```python
    def _pass2(self, program):
```
- **Python Pass 2:** First analyzes global statements. Then iterates through functions. If a function hasn't been analyzed (triggered by a call during global analysis), it calls `_analyze_func_body`.

```python
    def _single_pass(self, program):
```
- **C/C++ Pass:** Iterates functions, registers them, and immediately analyzes their bodies. Then analyzes global statements. Enforces strict define-before-use semantics.

**Function Body Analysis:**
```python
    def _analyze_func_body(self, func):
```
- `self._analyzed.add(func.name)` -> Marks as analyzed to prevent infinite recursion if a function calls itself.
- Sets `self.current_function = func` and calls `_enter_scope()`.
- Iterates `func.params`. If a param type is `UNKNOWN` (common in Python), it defaults it to `DataType.INT` as a fallback, or uses the inferred type from a function call if available. It `_declare`s each parameter in the local scope.
- Iterates `func.body` calling `_analyze_stmt`.
- Checks for `ReturnStmt` to infer the function's actual return type based on what it returns.
- Exits scope and resets `current_function`.

**Statement Dispatching:**
```python
    def _analyze_stmt(self, node):
```
- Huge `if/elif` block. Uses `isinstance` to route the AST node to the correct handler. E.g., `IfStmt` goes to `_do_if`.

**Individual Statement Handlers (Highlights):**
- `_do_var_decl`: Resolves the type of the assigned value. If the variable type is UNKNOWN, sets it to the resolved type (Type Inference!). Then `_declare`s it.
- `_do_assign`: Looks up the variable. If not found, errors. Resolves value type. Allows silent promotion of INT to FLOAT if a float is assigned to an int variable, otherwise errors on type mismatch.
- `_do_arr_assign`: Validates target is declared AND is an array. Validates index is an INT.
- `_do_if` / `_do_while`: Validates condition type. Enters scope, analyzes body, exits scope.
- `_do_for_range`: Enters scope, explicitly `_declare`s the loop variable as an INT, analyzes body, exits scope.
- `_do_for_each`: Looks up the array. Errors if not an array. Gets the array's element type. Enters scope, declares loop variable with that element type.

**Expression Type Resolution:**
```python
    def _resolve_type(self, node) -> DataType:
```
- Recursively evaluates an expression and returns its `DataType`.
- `Literal`: Returns its innate type.
- `Var`: Looks it up via `_resolve_var`, returns its registered type.
- `BinaryOp`: Recursively resolves left and right operands, then uses `_promote`.
- `FunctionCall`: Uses `_resolve_call`. Validates existence, arg count, arg types. If function hasn't been analyzed, it pauses, analyzes the function body to infer its return type, and then continues!

```python
    def _promote(self, a, b):
```
- Core type math. If `a` or `b` is UNKNOWN, returns the other. If either is FLOAT, result is FLOAT. INT+INT=INT.

4. ALGORITHMS DEEP DIVE
==================================================

**Deep Dive 1: Two-Pass Semantic Analysis (Forward-Call Resolution)**
*Scenario:* Python code:
```python
def main():
    print(add(2, 3))
def add(a, b):
    return a + b
main()
```
*Step-by-step Trace:*
1. `_pass1` starts.
2. Sees `main`. Registers `main` in `functions` and global scope. No params, return VOID.
3. Sees `add`. Registers `add` in global scope. Params `a` (UNKNOWN), `b` (UNKNOWN).
4. `_pass1` ends.
5. `_pass2` starts. Runs global statements. Finds `main()`.
6. Resolves call to `main`. `main` is in table. But `main` is not in `_analyzed`.
7. Calls `_analyze_func_body(main)`.
8. Enters scope. Body has `print(add(2, 3))`.
9. `_resolve_type` on `add(2, 3)`.
10. `add` is in table! (Thanks to Pass 1). Arg count (2) matches.
11. Maps `Literal(2, INT)` to param `a`. Updates param `a` type to `INT`. Same for `b`.
12. `add` is not in `_analyzed`. Calls `_analyze_func_body(add)`.
13. Enters scope for `add`. Declares `a` and `b` as INTs in local scope.
14. Body has `return a + b`. `_resolve_binop` sees INT+INT = INT.
15. Returns `INT`. Updates `add` return type to `INT`.
16. Exits `add` analysis. Call to `add` resolves to `INT`.
17. `print` accepts `INT`.
18. Exits `main` analysis.
19. `_pass2` function loop skips `main` and `add` because they are in `_analyzed`. Done!

**Deep Dive 2: Scope Checking & Variable Shadowing**
*Scenario:*
```python
x = 10
if True:
    x = 20
    y = 30
```
*Trace:*
1. Global scope: `scope_stack = [{}]`.
2. `x = 10`: `_do_var_decl`. Type INT. `scope_stack[0]` becomes `{'x': INT}`.
3. `IfStmt` encountered. `_do_if` runs.
4. `_enter_scope()`: `scope_stack` becomes `[{'x': INT}, {}]`.
5. `x = 20`: `_do_assign`. Calls `_lookup('x')`. Searches backwards. Empty dict? No. Global dict? Yes, finds 'x'. Validates INT assignment.
6. `y = 30`: `_do_var_decl`. Declares in innermost scope. `scope_stack` becomes `[{'x': INT}, {'y': INT}]`.
7. Exit `if` body. `_exit_scope()` pops the stack.
8. `scope_stack` reverts to `[{'x': INT}]`. Variable `y` is wiped from memory, correctly simulating scope death.

**Deep Dive 3: AST to IR Transformation**
Our architecture defines IR as the validated AST. 
The algorithm:
1. `IRGenerator.generate()` receives the AST.
2. It walks every node. It does *not* modify them. It asserts structural invariants (e.g., `BinaryOp` must have `.left` and `.right` which must be ASTNodes).
3. Once validated, the AST passes forward to the generator.
4. For the UI, `to_dict()` fires. It translates `BinaryOp('+', Var('x'), Literal(5))` into:
`{"node": "BinaryOp", "op": "+", "left": {"node": "Var", "name": "x"}, "right": {"node": "Literal", "value": 5}}`
This exact JSON is sent to the frontend.

5. ERROR HANDLING + EDGE CASES
==================================================

**Semantic Errors Detected:**
- **Undeclared Variables:** `_lookup` returns None. Handled in Assign, ArrayAssign, Var, ArrayAccess.
- **Redeclaration:** `_declare` checks if name already in *current* scope. Note: shadowing (declaring `x` in global, and `x` in local) is allowed because they are in different scope dicts.
- **Type Mismatches:** Handled in `_do_assign`. Cannot assign FLOAT to INT without explicit cast (which our simplified transpiler rejects).
- **String Operations:** Checked in `_resolve_binop`. If `DataType.STR` is found in an operation, errors out. "String operations are not supported".
- **Invalid Array Index:** Handled in `_do_arr_assign` and `_resolve_arr_acc`. Array index must be INT.
- **Missing Functions/Arg Count:** `_resolve_call` checks if `name` in `self.functions`, then checks `len(args) == len(params)`.
- **Return Outside Function:** `_do_return` checks if `self.current_function is None`.

**IR Edge Cases Detected:**
- **Missing Fields:** Empty variable names, missing conditions in `while`/`if`, missing operators in `BinaryOp`.
- **Negative Array Sizes:** Caught in `_chk_array_decl`.

**Common Bugs & Debugging Strategies:**
- *Bug:* Variables keep coming up as `UNKNOWN` type.
  *Fix:* The `_resolve_type` recursion might be failing, or `Literal` nodes aren't being parsed with their innate types. Check `ast_nodes.py` to ensure `DataType.UNKNOWN` is properly replaced.
- *Bug:* UI symbol table doesn't show local variables.
  *Fix:* Look at `_declare`. Ensure the key generated uses `current_function.name + "." + name` so global keys don't overwrite local ones.

6. ARCHITECTURAL DESIGN REASONING
==================================================

**Why Two-Pass for Python but One-Pass for C/C++?**
C and C++ are strictly "define before use" languages. A C compiler reads top-to-bottom. If you call `foo()` before declaring it, the C compiler throws an error. Therefore, a single-pass `_single_pass` accurately mimics C/C++ compiler rules.
Python allows function calls at the bottom of the file to functions defined above them, even if those functions call each other in complex ways. A single pass would crash on the first call to an unseen function. Two-pass solves this elegantly by registering the "table of contents" first.

**Why a Neutral AST as IR?**
A traditional compiler (like GCC) translates C to Assembly. It needs a low-level IR (like TAC) to bridge the gap.
We are a *Transpiler* translating high-level code (Python) to high-level code (C++). If we broke `x = a + b * c` into `t1 = b * c; t2 = a + t1; x = t2`, we would generate terrible, unreadable C++ code. We kept the AST as the IR because preserving the high-level program structure is paramount for source-to-source translation.

**Why Semantic Analysis *Before* IR?**
Usually, compilers do Parse -> IR -> Semantic (on IR) -> Target.
Because our IR *is* the AST, we perform Semantic Analysis directly on the AST. The IR Generator phase is technically an "Integrity and Serialization" phase that acts as the final gatekeeper before Code Generation. It proves the semantic phase didn't accidentally corrupt the AST structure.

**Why collect all errors?**
If a student runs the transpiler and has 5 undefined variables, crashing on the first one means they fix it, re-run, find the second, fix it, re-run. This is frustrating. By collecting errors in a list and raising a custom `CompilerErrorList` exception, we provide a modern developer experience (like Rust or modern TS).

7. VIVA / EXAMINER PREPARATION
==================================================

**Q: What is the main purpose of the Semantic Analysis phase in your transpiler?**
**Ideal Answer:** Its primary role is to enforce type checking and scope rules. It walks the Abstract Syntax Tree (AST) to ensure variables are declared before use, types are compatible in operations, function calls have correct arguments, and it builds a Symbol Table for the UI and code generators.

**Q: Explain how you handle variable scope.**
**Ideal Answer:** We use a stack of dictionaries (`self.scope_stack`). The global scope is at index 0. When entering a block like a function or loop, we push a new empty dictionary. When looking up a variable, we search backwards from the top of the stack to the bottom. When exiting a block, we pop the top dictionary, effectively destroying the local variables, mirroring how memory stack frames work.

**Q: Why does your Python semantic analyzer use two passes?**
**Ideal Answer:** To support forward declarations. In Python, you can call a function that is defined later in the file. A single-pass analyzer would throw an "undeclared function" error. Our Pass 1 collects all function signatures into the global scope. Pass 2 then evaluates the statements, knowing all function definitions in advance.

**Q: How does type inference work in your project?**
**Ideal Answer:** Python doesn't have explicit type declarations. Our AST initializes variables as `DataType.UNKNOWN`. When we see an assignment like `x = 5`, the `_resolve_type` method evaluates the right-hand side. It sees `Literal(5)`, determines it's an `INT`, and promotes `x`'s type to `INT` in the symbol table. 

**Q: Why didn't you use Three-Address Code (TAC) or LLVM IR for your Intermediate Representation?**
**Ideal Answer:** Because we are building a Source-to-Source transpiler, not a traditional compiler targeting assembly. TAC flattens complex expressions (`a + b * c`) into sequential temp variables. If we used TAC, our generated C++ code would look like assembly language, losing all human readability. Using a language-neutral AST as our IR perfectly preserves the high-level structure required to generate idiomatic C/C++/Python code.

**Q: What happens if I assign a float value to an int variable?**
**Ideal Answer:** Our semantic analyzer catches it. In `_do_assign`, we compare the resolved type of the value with the registered type of the variable. If a float is assigned to an int, we append a type mismatch `CompilerError` to our error list.

**Q: What is the purpose of the `ir_generator.py` file if the AST is already the IR?**
**Ideal Answer:** It serves two distinct purposes. First, it acts as a structural integrity firewall, asserting that the semantic analyzer didn't produce a malformed tree (e.g., a BinaryOp missing an operand). Second, it implements the serialization logic (`to_dict()`) that recursively converts the Python Dataclasses into JSON so the web frontend can visualize the tree structure.

  - Don't crash immediately. Append `CompilerError` to `self.errors`.
  - Raise `CompilerErrorList` at the end of the phase to show all errors.
